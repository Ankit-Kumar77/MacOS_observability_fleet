1. What this is

Ansible deploys host-metric observability to a fleet of Mac Minis. One Mac runs VictoriaMetrics and Grafana; every other Mac runs the OpenTelemetry Collector. This branch is the main deployment re-built to need no sudo: everything installs under the deployment user's home and runs as per-user LaunchAgents.

3. Prerequisites

  • Ansible control machine with the full ansible package (not bare ansible-core; ansible.cfg uses the community.general yaml callback).
  • SSH access to every Mac as the deployment user. No sudo needed.
  • inventories/production/hosts.yml filled in: exactly one host in monitoring_server with ansible_host set, the rest in monitored_nodes. The committed file holds REPLACE_WITH_* placeholders; keep real addresses out of Git.
  • Workers must reach the monitoring Mac on the VictoriaMetrics port, and the collector needs the Local Network privilege if the two are on the same subnet (section 7).

4. Deploy

# Static checks, no hosts touched
ansible-playbook site.yml --syntax-check
ansible-lint

# Connectivity
ansible all -m ping

# Everything (as the normal user, never --ask-become-pass)
ansible-playbook -i inventories/production/hosts.yml site.yml

# Server first, then one worker, then the rest
ansible-playbook -i inventories/production/hosts.yml site.yml --tags server
ansible-playbook -i inventories/production/hosts.yml site.yml --tags agent --limit <worker>
ansible-playbook -i inventories/production/hosts.yml site.yml --tags agent

# Health/verification only
ansible-playbook -i inventories/production/hosts.yml site.yml --tags verify

Each role runs: preflight checks → install/configure → restart changed services → verify. Preflight fails, before writing anything, if the play runs as root or with become, the per-user launchd domain is missing, the old system-level stack is present without side-by-side mode, or a needed port is taken.

5. Verify

The agent play ends with an end-to-end check against VictoriaMetrics. To check by hand:

# On the monitoring Mac: hosts reporting memory metrics
curl -s 'http://127.0.0.1:<victoriametrics_port>/api/v1/query' \
  --data-urlencode 'query=count by (host_name) (system_memory_usage_bytes)'

# Total series ingested (must not be empty)
curl -s 'http://127.0.0.1:<victoriametrics_port>/api/v1/query' \
  --data-urlencode 'query=count({__name__=~".+"})'

# On a worker: the collector's own counters
curl -s http://127.0.0.1:18888/metrics \
  | grep -E '^otelcol_(receiver_accepted|exporter_sent|exporter_send_failed)_metric_points'

# On any Mac: agent state
launchctl print user/$(id -u)/com.observability.user.otelcol | grep -E 'state|pid'
A /health 200, or a 400 for an empty POST, only shows that VictoriaMetrics answers. Metrics are arriving only when count by (host_name) (system_memory_usage_bytes) lists the worker and otelcol_exporter_sent_metric_points rises.

6. Side-by-side with the old system-level stack

Where the old main deployment is still running and cannot be removed, enable side-by-side mode fleet-wide so the server and every worker agree on the port:

ansible-playbook -i inventories/production/hosts.yml site.yml -e observability_side_by_side=true
# or set observability_side_by_side: true in inventories/production/group_vars/all.yml
  • The new VictoriaMetrics moves to 8429 and Grafana to 3001; datasource and every collector follow.
  • The new collector's internal metrics stay on 127.0.0.1:18888; the old collector keeps 8888.
  • The old stack is only ever read (plist stat, launchctl print system/<label>). Nothing under /Library/LaunchDaemons or /opt/observability is stopped, unloaded, modified or deleted, and VictoriaMetrics data is never shared.
  • Re-run both plays when toggling the mode.

7. Known issue: Local Network Privacy blocks the worker collector

Symptom. The worker collector LaunchAgent is running and collecting metrics, but none reach VictoriaMetrics. Its error log repeats dial tcp <monitoring-mac>:<port>: connect: no route to host for both otlphttp and tcp_check. Yet curl to the same address over SSH returns 200, ping and ARP are fine, and the old root collector keeps working. launchctl kickstart changes nothing. The agent play fails at Wait for host metrics to arrive in VictoriaMetrics with a message naming Local Network Privacy.

Observed on the first side-by-side deployment

Collector counter (worker, 127.0.0.1:18888)Value
otelcol_receiver_accepted_metric_points{receiver="hostmetrics"}27,675
otelcol_receiver_accepted_metric_points{receiver="tcp_check/monitoring_server"}248
otelcol_receiver_accepted_metric_points{receiver="otlp_json_file/ssh_state"}335
otelcol_exporter_send_failed_metric_points{exporter="otlphttp"}8,277
Hostmetrics scraper errors0

Collection works; only the outgoing connection from the LaunchAgent fails.

Cause

Since macOS 15, programs need the Local Network privilege to open connections to addresses on a directly attached subnet. Apple's TN3179 lists what macOS allows automatically: any launchd daemon, any program running as root, and command-line tools run from Terminal or over SSH (and their children). It adds: "The exception for launchd daemons doesn't apply to launchd agents." A blocked TCP connect fails with EHOSTUNREACH, which Go prints as no route to host.

Old collector (root LaunchDaemon)exemptworks
curl / nc / Ansible tasks over SSHexemptworks
New collector (com.observability.user.otelcol, LaunchAgent)needs the privilegeno route to host until granted
Status: this diagnosis fits all the evidence but has not yet been confirmed on a Mac Mini. It does not apply when the monitoring Mac is reached through a router (a different subnet).

Confirm on a worker (read-only, no sudo)

sw_vers                                                    # macOS 15 or later?
nc -vz -G 3 <monitoring-mac-ip> <victoriametrics_port>    # over SSH: expected to succeed
curl -s http://127.0.0.1:18888/metrics \
  | grep -E '^otelcol_exporter_(sent|send_failed)_metric_points'   # sent flat, failed rising
grep 'no route to host' ~/tools/observability/var/log/otelcol.err.log | tail -2   # current timestamps

Remediation (needs the console user or an administrator)

The playbook cannot grant this privilege and deliberately does not work around the policy.

OptionWhoStepsCaveats
1. Grant the privilege per worker Deployment user, at the console. No sudo. Log in at the worker's console as the deployment user while the collector agent is running. Allow otelcol-contrib in the Local Network alert, or enable it under System Settings → Privacy & Security → Local Network. Then re-run the agent play for that Mac. The release binary is ad-hoc signed (Identifier=a.out); macOS tracks the privilege by code signature, so expect to grant it again after each collector upgrade. One Mac at a time. Not yet confirmed on a Mac Mini.
2. Exempt the monitoring Mac's address Administrator / IT 
sudo defaults write com.apple.network.local-network \
  AllowedEthernetLocalNetworkAddresses -array-add "<monitoring-mac-ip>/32"
# Wi-Fi: AllowedWiFiLocalNetworkAddresses
Restart the worker, then re-run the agent play (LaunchAgents do not start at boot).		 macOS 15.5+. Applies to every program on that Mac for that one address. Apple states MDM cannot configure Local Network Privacy; this preference is the documented per-Mac route.
3. Use the system-level deployment Administrator Deploy main (root LaunchDaemon), which is exempt. Needs sudo; that is what this branch avoids.

Fixed alongside: collector port clash on 8888

Earlier builds of this branch left the collector's internal telemetry on its default 127.0.0.1:8888, which the old collector already holds, so the new collector exited with bind: address already in use. It now uses otel_internal_metrics_port (18888), checked by preflight and kept distinct from 8888 in side-by-side mode.

10. Operating the agents

# Status
launchctl print user/$(id -u)/com.observability.user.otelcol
launchctl list | grep com.observability.user

# Restart in place
launchctl kickstart -k user/$(id -u)/com.observability.user.otelcol

# Logs
tail -f ~/tools/observability/var/log/otelcol.err.log

# Validate plists and collector config
plutil -lint ~/Library/LaunchAgents/com.observability.user.*.plist
~/tools/observability/bin/otelcol-contrib validate --config=$HOME/tools/observability/etc/otel-config.yaml

Re-running the play (optionally --limit <host>) always returns a Mac to its intended state. To remove the stack from a Mac (no sudo): boot out each com.observability.user.* label, delete the four plists from ~/Library/LaunchAgents, then delete ~/tools/observability.

Preflight: found the system-level deploymentEnable observability_side_by_side, or have an admin remove the old stack.

12. Validation status

Verified on one Apple Silicon Mac (macOS 27, no sudo, local connection): syntax check and ansible-lint pass; full playbook failed=0 and a second run changed=0; side-by-side mode on 8429 / 3001 / 18888 with a stand-in listener on 8888; host metrics ingested with the expected host_name; every dashboard panel returns data; preflight guards fail before writing anything.
Reported from the monitoring Mac deployment (side-by-side): VictoriaMetrics on 8429 and Grafana on 3001 running as LaunchAgents, datasource and both dashboards provisioned, server verification passed, old stack on 8428 / 3000 untouched.
Not yet verified on Mac Minis: worker metrics reaching the new VictoriaMetrics (blocked, section 7); the Local Network Privacy remediation; agents surviving the end of the SSH session, logout and reboot; SSH state against a real sshd with live sessions; 20+ hosts at once.
