1. Overview

This deployment monitors a fleet of Mac Minis using Ansible. One Mac (the monitoring server) stores and displays metrics; every other Mac (a worker) collects and sends them. All software installs under the deployment user's home directory and runs as per-user LaunchAgents, so no administrator access is required.

2. Prerequisites

  • An Ansible control machine with the full ansible package installed.
  • SSH access to every Mac as the deployment user.
  • inventories/production/hosts.yml completed: one host under monitoring_server (with ansible_host), all others under monitored_nodes.
  • Workers can reach the monitoring server on port 8429.
  • Each worker's collector has the macOS Local Network permission (see Known issue).

3. Deployment

Run from the repository root on the control machine. Never add --ask-become-pass.

# 1. Check the playbook and connectivity
ansible-playbook site.yml --syntax-check
ansible all -m ping

# 2. Deploy the monitoring server
ansible-playbook -i inventories/production/hosts.yml site.yml --tags server -e observability_side_by_side=true

# 3. Deploy one worker and confirm its metrics appear
ansible-playbook -i inventories/production/hosts.yml site.yml --tags agent -e observability_side_by_side=true --limit <worker>

# 4. Deploy the remaining workers
ansible-playbook -i inventories/production/hosts.yml site.yml --tags agent -e observability_side_by_side=true

observability_side_by_side=true selects ports 8429 and 3001. Use the same value for the server and every worker. Each run checks the target first, installs or updates only what changed, and finishes with automatic verification. Runs are safe to repeat.

4. Verification

The playbook verifies each Mac automatically. To check manually:

# Monitoring server: hosts currently sending memory metrics
curl -s 'http://127.0.0.1:8429/api/v1/query' \
  --data-urlencode 'query=count by (host_name) (system_memory_usage_bytes)'

# Worker: collector counters (exported should rise, failed should stay flat)
curl -s http://127.0.0.1:18888/metrics \
  | grep -E '^otelcol_(receiver_accepted|exporter_sent|exporter_send_failed)_metric_points'

# Any Mac: service state
launchctl print user/$(id -u)/com.observability.user.otelcol | grep -E 'state|pid'
A worker is reporting correctly only when it appears in the host_name query and its otelcol_exporter_sent_metric_points count rises. A successful /health response alone does not confirm that metrics are being received.

Then open Grafana at http://<monitoring-server>:3001 and check that the worker appears on the Fleet Overview dashboard.

5. Known issue: worker metrics blocked by Local Network Privacy

Symptom

  • The worker collector is running and collecting data, but nothing arrives in VictoriaMetrics.
  • ~/tools/observability/var/log/otelcol.err.log repeats connect: no route to host for the monitoring server.
  • Manual tests over SSH (curl, ping) to the same address succeed.
  • The deployment fails at Wait for host metrics to arrive in VictoriaMetrics, with a message naming Local Network Privacy.

Cause

Since macOS 15, an application needs the Local Network permission to connect to other devices on the same subnet. Commands run over SSH are exempt, which is why manual tests succeed. Background LaunchAgents such as the collector are not exempt (Apple TN3179). macOS reports the blocked connection as "no route to host". The network, ports and VictoriaMetrics are working correctly.

This diagnosis matches all observed evidence but has not yet been confirmed on a Mac Mini.

Confirm (read-only, on the worker)

sw_vers                                                   # macOS 15 or later
nc -vz -G 3 <monitoring-server-ip> 8429                  # succeeds over SSH
grep -c 'no route to host' ~/tools/observability/var/log/otelcol.err.log

Resolution

The permission can only be granted at the Mac itself or by an administrator; the playbook does not bypass it. Choose one:

OptionPerformed bySteps
A. Allow the collector Deployment user, at the Mac's screen Log in on the worker as the deployment user. Allow otelcol-contrib when macOS asks, or enable it under System Settings → Privacy & Security → Local Network. Re-run the worker deployment. Repeat after each collector upgrade.
B. Allow the monitoring server's address IT / administrator On each worker run the command below, restart the Mac, then re-run the worker deployment. 
sudo defaults write com.apple.network.local-network \
  AllowedEthernetLocalNetworkAddresses -array-add "<monitoring-server-ip>/32"
For Wi-Fi, use AllowedWiFiLocalNetworkAddresses. Requires macOS 15.5 or later.

Option B is recommended for the fleet: it is applied once per Mac and does not need repeating after upgrades.
